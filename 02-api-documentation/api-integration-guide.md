# Developer Integration Guide: Stripe Payment Method Configurations

## 1. Overview

### Purpose

This guide explains how to obtain Stripe API credentials, authenticate requests, create and verify a Payment Method Configuration, and use the configuration in a supported checkout flow.

Payment Method Configurations control payment-method availability and display preferences. A configuration does not charge a customer by itself.

### Intended audience

This guide is intended for backend developers, API integrators, and developers responsible for implementing Stripe checkout workflows.

### Prerequisites

Before you begin, ensure that you have:

- A Stripe account.
- Access to the Stripe Dashboard and API keys.
- A test-mode secret API key.
- A backend environment that can make HTTPS requests.
- `curl` or an equivalent HTTP client.
- Basic knowledge of HTTP, JSON, and environment variables.

**Official documentation:** https://docs.stripe.com/api/payment_method_configurations

## 2. Understand the integration workflow

The integration consists of two related workflows:

1. Configure the payment methods available to the checkout experience.
2. Create a checkout or payment request that uses the configuration.

```text
Stripe Dashboard
       |
       v
Obtain test API credentials
       |
       v
Configure server-side authentication
       |
       v
Create a Payment Method Configuration
       |
       v
Retrieve and verify the configuration
       |
       v
Use the configuration in a supported checkout flow
       |
       v
Verify the payment outcome
```

The configuration workflow and the payment-processing workflow are separate. A successful configuration request does not indicate that a customer payment has succeeded.

## 3. Obtain Stripe API credentials

### Step 1: Sign in to Stripe

Open the Stripe Dashboard:

https://dashboard.stripe.com/

Navigate to the API keys section:

https://dashboard.stripe.com/apikeys

### Step 2: Select the correct environment

Use test mode while developing and validating the integration.

Stripe secret keys typically use these prefixes:

| Key type | Prefix | Purpose |
|---|---|---|
| Test secret key | `sk_test_` | Authenticates server-side requests in test mode. |
| Live secret key | `sk_live_` | Authenticates server-side requests in live mode. |
| Test publishable key | `pk_test_` | Used by supported client-side integrations in test mode. |
| Live publishable key | `pk_live_` | Used by supported client-side integrations in live mode. |
| Restricted API key | `rk_` | Provides limited permissions according to its configuration. |

Use a secret or appropriately restricted key for the server-side API operations in this guide.

A webhook signing secret, which commonly begins with `whsec_`, is used to verify webhook signatures. It is not a substitute for an API key.

### Step 3: Protect the credentials

Never include a real secret key in:

- Frontend JavaScript or mobile application code.
- Public GitHub repositories.
- Screenshots or published documentation.
- Application logs or error messages.

If a key is exposed, revoke or rotate it promptly.

## 4. Configure the environment

Set the test secret key as an environment variable.

Example for Bash:

```bash
export STRIPE_SECRET_KEY="sk_test_REPLACE_WITH_YOUR_TEST_KEY"
```

Replace the placeholder with your own test key. Do not commit the key or a file containing the key to source control.

For production systems, use an approved secrets manager or protected environment configuration.

Verify that the variable is available to your process without printing the key itself.

```bash
if [ -n "$STRIPE_SECRET_KEY" ]; then
  echo "Stripe API key is configured."
else
  echo "Stripe API key is not configured."
fi
```

## 5. Understand Stripe authorization

Stripe API requests use HTTP Basic authentication.

With `curl`, supply the secret key as the username and an empty password. The trailing colon tells `curl` that the password is empty.

Example:

```bash
curl https://api.stripe.com/v1/payment_method_configurations \
  -u "$STRIPE_SECRET_KEY:"
```

The request uses HTTPS and sends the API key through the Authorization header generated by `curl`.

Do not manually place the secret key in a URL or query parameter.

For further information, see:

https://docs.stripe.com/api/authentication

## 6. Create a Payment Method Configuration

### Step 1: Send the request

**Endpoint:** `POST /v1/payment_method_configurations`

The following example creates a configuration by name.

```bash
curl https://api.stripe.com/v1/payment_method_configurations \
  -u "$STRIPE_SECRET_KEY:" \
  -d "name=Website checkout configuration"
```

### Step 2: Inspect the response

A successful request returns a Payment Method Configuration object. The following shortened JSON is illustrative:

```json
{
  "id": "pmc_example123",
  "object": "payment_method_configuration",
  "active": true,
  "name": "Website checkout configuration"
}
```

### Step 3: Save the configuration ID

Store the returned `id` in your application's configuration or database, as appropriate.

Use the actual ID returned by Stripe. The sample value `pmc_example123` is a placeholder.

The configuration ID identifies the resource; it is not an authentication credential.

## 7. Retrieve and verify the configuration

### Step 1: Send a GET request

Replace the placeholder with the ID returned by the create operation.

```bash
curl https://api.stripe.com/v1/payment_method_configurations/pmc_example123 \
  -u "$STRIPE_SECRET_KEY:"
```

### Step 2: Verify the response

Check the following:

- The returned `id` matches the configuration you created.
- The configuration has the expected active state.
- The name and applicable settings match your requirements.
- The relevant payment methods are available and configured as expected.

For Connect child configurations, review the applicable parent relationship and payment-method availability and display-preference fields.

If the response does not match your expectations, review the configuration settings before proceeding.

## 8. Update the configuration when required

Use the documented update endpoint to change a configuration.

**Endpoint:** `POST /v1/payment_method_configurations/{configuration_id}`

For example, the following request sets a configuration's active state to `true`:

```bash
curl https://api.stripe.com/v1/payment_method_configurations/pmc_example123 \
  -u "$STRIPE_SECRET_KEY:" \
  -d "active=true"
```

Inspect the returned object to confirm that the change was applied.

Only update fields supported by the endpoint and applicable to the configuration type. Payment-method-specific display preferences have their own documented parameters.

## 9. Use the configuration in checkout

Creating a configuration is not enough to accept a payment. Your application must use a supported payment integration.

Stripe recommends considering Checkout Sessions for most integrations because it handles more of the checkout workflow.

Official reference:

https://docs.stripe.com/api/checkout/sessions/create

### Step 1: Create a Checkout Session

The following example illustrates a server-side Checkout Session request with a configuration ID.

```bash
curl https://api.stripe.com/v1/checkout/sessions \
  -u "$STRIPE_SECRET_KEY:" \
  -d "mode=payment" \
  -d "line_items[0][price]=price_REPLACE_WITH_PRICE_ID" \
  -d "line_items[0][quantity]=1" \
  --data-urlencode "success_url=https://example.com/success" \
  -d "payment_method_configuration=pmc_REPLACE_WITH_CONFIGURATION_ID"
```

Replace the price and configuration placeholders with valid IDs from the intended Stripe account.

This example assumes a supported configuration and checkout scenario. Confirm the required parameters, account context, and configuration compatibility against the current Stripe API reference.

### Step 2: Handle the Checkout Session response

Inspect the response and obtain the Checkout Session information needed by your application.

For a hosted checkout integration, use the returned session URL according to Stripe's documented redirect flow. Do not assume that the configuration API returns a checkout URL.

### Step 3: Complete and verify payment

The customer completes the checkout flow. Your backend should verify the payment outcome using Stripe's documented payment lifecycle and webhook handling.

Do not fulfill an order solely because a configuration was created, a Checkout Session was created, or the customer returned to a success URL.

## 10. Error handling

Handle errors at both the configuration and checkout stages.

| Symptom | Possible cause | Recommended action |
|---|---|---|
| `401 Unauthorized` | Invalid or missing API key. | Verify the key and authentication syntax. |
| `403 Forbidden` | The account or key lacks required access. | Review permissions and account context. |
| `404 Not Found` | Configuration or other referenced resource cannot be found. | Verify resource IDs and account context. |
| `400 Bad Request` | Invalid or unsupported parameter. | Compare the request with the endpoint schema. |
| `429 Too Many Requests` | Rate limiting. | Reduce request frequency and follow retry guidance. |
| Checkout request fails | Invalid price, configuration, or required parameters. | Validate the Checkout Session request and resource IDs. |
| Network timeout | The request outcome may be unknown. | Check the operation's status before attempting a potentially duplicative operation. |

Inspect Stripe's error response and request identifier when diagnosing failures. Use stable error codes where available rather than relying on message text.

## 11. Security considerations

- Use secret keys only on the server.
- Use test credentials during development.
- Store keys in environment variables or a secrets manager.
- Use HTTPS for all API requests.
- Never commit secrets to Git.
- Restrict key permissions where appropriate.
- Verify payment status on the server before fulfilling an order.
- Verify webhook signatures using the appropriate webhook signing secret.
- Avoid logging secret keys or sensitive payment information.
- Follow Stripe's guidance for retrying requests and handling duplicate webhook events.

## 12. Troubleshooting

### The API key is not recognized

Check that the key is configured correctly, belongs to the intended Stripe account, and matches the environment being used.

### The configuration cannot be retrieved

Confirm that the configuration ID was copied correctly and that the request uses the appropriate account context.

### The payment method does not appear at checkout

Check the configuration's effective display preference, account eligibility, supported payment flow, and transaction requirements. A configuration does not guarantee that every payment method is available to every customer.

### The configuration request succeeds but payment fails

Configuration management and payment processing are separate operations. Inspect the Checkout Session or payment object, review the payment status, and follow Stripe's documented error-handling guidance.

### The payment appears successful in the browser but the order is not updated

Verify the payment outcome on the backend and review webhook delivery and processing. Do not use a browser redirect alone as proof of payment.
